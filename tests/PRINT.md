# 真实 Chrome 打印验收

当前状态（2026-11-06）：以下历史阻塞中的离屏公式、空白页和文末浅色矩形已修复。最新证据见文末；历史失败样本保留。

平台：Windows amd64，Chrome 156.0.8078.49，Milkdown/Crepe 7.23.0。仅自动化浏览器，没有操作桌面或文件管理器。验收使用有窗口的 Chrome，不使用 `Page.printToPDF`。

## 实际流程

`node scripts/verify-print.mjs` 在独立工作区和浏览器配置中：

1. 打开真实程序、登录、编辑含中文、宽表格、90 行长代码、块公式、1600×1000 图片及 30 节正文的笔记。
2. 打开应用的只读打印快照，并从真实按钮进入 Chrome 原生打印预览，确认目标为“另存为 PDF”和 A4。
3. 点击原生取消按钮，返回应用、继续编辑并完成保存，确认没有生成文件。
4. 在同一已核实只有 PDF 目标的隔离配置中，以 Chrome 的 kiosk-printing 模式自动确认 PDF 保存，取得真实 Skia/PDF 输出。该模式只用于开发验收，不是产品依赖，也未调用其他 PDF 引擎。
5. 保存生成的 PDF、预览截图、准备好的正文 HTML 和验证 JSON 到忽略的 `tests/artifacts/native-print-*`。

脚本在公式未渲染时返回非零状态，不能把“生成了文件”当作内容验收通过。

## 已修复并验证

- 首次 PDF 中 90 个长代码行尾标记全部缺失。通过公开 `CodeMirror` feature config 的 `extensions` 设置 `EditorView.lineWrapping` 后，180 个行首/行尾标记均能从实际 PDF 中提取。
- 通过公开 `setCodeMirrorTheme` 与 `EditorView.theme` 让编辑与打印使用同一个浅色代码主题，解决浅色背景上的低对比度代码。
- 以标准的 `role="textbox"`、`contenteditable="false"` 属性约束打印内边距，不引用 Milkdown 私有类名。打印布局浏览器测试检查行尾的真实位置与文字可读性。
- 真实 PDF 中包含中文标题及正文、宽表格两端标记和一幅大图，未发现应用工具按钮或在线成员标签。Poppler 已渲染全部页面供视觉检查。
- 后续定位到预览宽度与 A4 正文宽度不一致，进入打印时长代码重新换行。将应用预览正文固定为 A4 减去两侧 15 mm 页边距的 180 mm，并统一只读正文内边距后，正式构建的真实 PDF `native-print-wl16p4` 包含全部 30 节、文末标记、90 个代码行首及 90 个行尾、宽表格两端和一幅大图；第 12 页视觉检查确认第 28–30 节及文末实际可见。浏览器测试同时检查预览与打印宽度相同。此修复只修改本项目 CSS，不修改第三方组件。

## 未通过，不能声明 PDF 完成

当前实际 PDF 仍有问题：

- 块公式位于初始视口之外时，官方组件只生成源码占位，尚无 MathML 渲染。实际 PDF 显示公式源码，不能满足公式语义与版面要求。
- 原先 12 页样本的文末缺失已经修复。但新的 13 页 PDF 在正文结束之后还有一张空白页，第 12 页文末下方有一条浅色矩形，打印版面仍不能标为全部通过。

可用开发环境的 Python 与 `pypdf` 运行 `python scripts/check-print-pdf.py <native-print.pdf>`，在 PDF 旁生成 `pdf-content.json`。它检查固定验收正文的节次顺序、每行代码首尾、中文标题、文末、表格边缘、图片、工具文字和空白页；旧样本会因缺失节次/文末失败，新样本会因空白页失败。它不代替公式渲染检查及视觉检查，不增加产品运行依赖。

已核对官方 7.23.0 包的公开 `CodeBlockConfig`：提供 extensions、previewOnlyByDefault、renderPreview 等配置，没有关闭离屏懒加载的公开选项。官方组件内部使用 IntersectionObserver 初始化离屏代码块，并在离屏后销毁实例。7.22.0 官方包亦有相同行为。npm 查询当时的最新官方版本仍为 7.23.0。

没有修改依赖、复制 NodeView、访问其私有初始化方法、引入第二渲染器或为失败改用其他导出引擎。仍保持当前锁定的 Milkdown 版本。用户于 2026-10-30 明确选择“保持零侵入，先完成其他验收”。这不取消原定 PDF 要求，当前仍不将打印功能标为验收完成。

上次发布包构建曾因自动审批额度中断；2026-11-03 恢复后已重新执行检查和五平台打包。当前 PDF 阻塞是上述可复现的渲染与版面问题。
